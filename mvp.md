# MVP Unified LLM Gateway

Документ фиксирует функциональные границы первой версии клиентского
приложения и основной сценарий использования.

## 1. Цель MVP

Дать разработчику или администратору шлюза единую консоль, в которой
можно:

- увидеть состояние провайдеров и маршрутов;
- понять, какие модели доступны клиентам;
- отправить тестовый запрос через шлюз;
- разобрать ошибочный запрос по попыткам и кодам ошибок;
- оценить стоимость запросов.

MVP не заменяет полноценную admin-панель и не реализует управление
данными. Его задача — проверить пользовательские сценарии, роутинг,
каркас страниц и переиспользование UI-библиотеки.

## 2. Акторы

| Актор | Описание |
|---|---|
| Разработчик | Запускает backend и frontend, проверяет API и маршруты |
| Администратор шлюза | Смотрит состояние провайдеров, ключей и запросов |
| Клиент API | Отправляет запросы в `POST /v1/chat/completions` |

## 3. Use case 1: тестовый запрос через песочницу

**Название:** отправить тестовый запрос к alias-модели.

**Актор:** разработчик.

**Предусловия:**

- backend запущен на `http://localhost:3000`;
- PostgreSQL запущен, миграции применены, seed выполнен;
- в БД есть провайдер, модель и alias `fast-model`;
- создан клиентский ключ `lgw_...`;
- frontend запущен на `http://localhost:5173`.

**Основной сценарий:**

1. Пользователь открывает `/playground`.
2. Выбирает alias модели, например `fast-model`.
3. Вводит клиентский ключ.
4. Вводит текст запроса.
5. Нажимает «Отправить запрос».
6. Frontend отправляет `POST /v1/chat/completions` через Vite proxy.
7. Backend выбирает провайдера и ключ, выполняет запрос.
8. Frontend показывает ответ и имя провайдера, который обслужил запрос.
9. Пользователь открывает `/requests`, находит запрос по `request_id`
   и проверяет попытки, latency и стоимость.

**Результат:**

- пользователь получил ответ модели;
- запрос сохранён в `request_logs` и `request_attempts`;
- в консоли видно, какой провайдер сработал и сколько стоил запрос.

**Альтернативные сценарии:**

| Ситуация | Поведение |
|---|---|
| Пустой клиентский ключ | Frontend показывает ошибку «Введите клиентский ключ» |
| Неверный ключ | Backend возвращает `401`, frontend показывает сообщение |
| Нет маршрута для alias | Backend возвращает `no_route`, frontend показывает ошибку |
| Провайдер недоступен | Router делает fallback; в ответе виден следующий провайдер |
| Все провайдеры упали | Backend возвращает `502 all_providers_failed` |
| Backend не запущен | Frontend показывает сетевую ошибку |

## 4. Use case 2: диагностика ошибочного запроса

**Название:** разобрать причину ошибки запроса.

**Актор:** администратор шлюза.

**Предусловия:**

- в журнале есть запрос со статусом `error` или с fallback-попытками;
- пользователь открыл консоль.

**Основной сценарий:**

1. Пользователь открывает `/requests`.
2. Находит нужный запрос по модели, клиенту или времени.
3. Открывает `/requests/:requestId`.
4. Видит итоговый статус, провайдера, токены и стоимость.
5. Изучает таблицу попыток: номер, провайдер, статус, код ошибки,
   latency.
6. По коду ошибки понимает причину: `provider_timeout`,
   `provider_unavailable`, `rate_limited` и т.д.
7. При необходимости открывает `/providers/:providerId` и проверяет
   состояние ключей и circuit breaker.

**Результат:**

- пользователь понимает, на каком провайдере и почему упал запрос;
- видит, сработал ли fallback;
- может принять решение о смене ключа, маршрута или провайдера.

**Альтернативные сценарии:**

| Ситуация | Поведение |
|---|---|
| Запрос не найден | Показывается `EmptyState` со ссылкой на журнал |
| Провайдер не найден | Показывается `EmptyState` со ссылкой на список |
| Журнал пуст | Показывается пустое состояние с подсказкой |

## 5. Границы MVP

### Входит в MVP

- Каркас frontend на React + TypeScript + Vite.
- Библиотека общих компонентов `@llm-gateway/ui`.
- Маршруты и страницы:
  - `/` — обзор;
  - `/providers` — список провайдеров;
  - `/providers/:providerId` — детали провайдера;
  - `/models` — маршруты моделей;
  - `/requests` — журнал запросов;
  - `/requests/:requestId` — детали запроса;
  - `/playground` — песочница с тестовым запросом;
  - `/settings` — защищённый раздел;
  - `/login` — вход в админ-сессию;
  - `*` — 404.
- Навигация без ошибок в консоли.
- Реальное использование минимум одного компонента библиотеки.
- Mock-данные для провайдеров и маршрутов.
- Реальный вызов `POST /v1/chat/completions` из песочницы.
- Журнал запросов и детали запроса из read-only API
  (`/api/requests`, `/api/requests/:requestId`).
- Защита `/settings` через `RequireAdmin` и `sessionStorage`.
- Юнит-тесты библиотеки и тесты роутинга frontend.
- ESLint, coverage и строгая типизация.

### Не входит в MVP

- CRUD провайдеров, моделей, маршрутов и ключей через UI.
- Реальная аутентификация администратора и роли.
- Загрузка провайдеров, моделей, маршрутов и ключей из admin API.
  Журнал запросов уже читается через read-only API.
- Графики, агрегаты и экспорт отчётов.
- WebSocket/SSE-обновления в реальном времени.
- Управление rate limit и лимитами клиентов.
- Ручной сброс circuit breaker из UI.
- Переключатель тёмной/светлой темы, i18n и мобильное приложение.
- Полноценный production reverse proxy и деплой.

## 6. Критерии приёмки MVP

1. `npm run lint`, `npm run test`, `npm run build` проходят в
   `web/frontend` и `web/ui-library`.
2. `npm run dev` запускает frontend на `http://localhost:5173`.
3. Все маршруты из `architecture.md` открываются без ошибок в консоли.
4. Переходы через sidebar и ссылки в таблицах работают.
5. `/settings` без сессии перенаправляет на `/login`, после входа
   возвращает на `/settings`.
6. Песочница отправляет запрос и показывает ответ или понятную ошибку.
7. UI library используется на страницах и имеет coverage не ниже 70%
   хотя бы по одному компоненту.
8. В исходном коде нет `any`, `require`, `module.exports` и `var`.
9. После ответа песочницы запрос находится в `/requests` по
   `X-Request-Id`, а `/requests/:requestId` показывает его попытки,
   latency и стоимость из backend.

## 7. Развитие после MVP

- Admin API и реальные данные вместо mock.
- CRUD провайдеров и ключей.
- Управление circuit breaker и cooldown.
- Графики стоимости и latency.
- Аудит действий администратора.
- Полноценная авторизация с ролями.
